# Combined RP2350 ("rack") — all four modules, live switch, C3 UI, mod engine

Goal: ONE firmware running the four accepted ports (Elements, Clouds, Plaits
98-engine, Rings MiniElements) with live module switching, a persistent
modulation engine, and a hardware UI on a separate ESP32-C3. Serial chaining
(A→B) is v2. Plan doc supersedes none of the per-port plans; the four ports
remain the audio truth — this project composes them.

## Hardware topology

```
[16 pots]─HC4067─┐
[encoder+sw]─────┤ ESP32-C3 (UI MCU, NimBLE)          DIN MIDI IN (6N138 opto)
[BLE-MIDI]───────┤  │  settings/switch cmds,           DIN MIDI OUT
[IPS SPI screen]─┘  │  BLE-MIDI as 4-byte pkts             │
                    ▼ UART 921600, framed                  ▼
        RP2350: UART ingest shim ─┐
        UART1 31250 DIN parser ───┤→ midiHandleEventPacket (ONE funnel:
        USB device + PIO-USB host ┘   device/host/DIN/BLE/UI all 4-byte pkts)
        core 1 render: [mod engine (persistent)] → active module(s) → I2S
```

Pin plan (RP2350): UART1 DIN on free GPIOs (final pins at bring-up; no
collisions with I2S 6/7/8, host 14/15, LED 22, native USB). C3↔RP2350 UART on
two more free GPIOs. C3: HC4067 = 1× ADC1 + 4 addr lines, encoder 2+1 GPIO,
screen = hardware SPI (SCK/MOSI/CS/DC/RST/BL). All 3.3 V.

## Decisions

| Decision | Choice | Why |
|---|---|---|
| UI MCU | ESP32-C3 via UART | Only part with a radio (BLE-MIDI must terminate there); isolates screen/mux/BLE from the proven audio cores |
| Switching | **Live swap**, no reboot | memcpy module's hot sections into the SRAM window (~60 ms, muted), placement-new state into the arena, Init, unmute |
| Mod engine | **DSP side**, core 1 loop-top, persistent object outside the arenas | Block-boundary alignment, MIDI-clock sync, survives swaps, future audio-rate path |
| Chaining | v2, after switching ships | Plaits@32k rate patch + routing; pair list below |
| MIDI funnel | Everything becomes 4-byte USB-MIDI event packets → existing `midiHandleEventPacket` | Zero changes to accepted module code; UI injects the same bytes the panels send |
| Common rate | 32 kHz for chaining (v2); per-module native rates while switched (48k plaits / 32k others) | Ring/Clouds heavy modes exceed budget at 48 kHz; Plaits at 32k = 1.5× cheaper |

## SRAM architecture (the hard part)

- **Arenas (main.cpp-side, no lib patches)**: object arena 128 KB (largest
  state = rings::Part 123.4 KB) + buffer arena 192 KB (clouds large+small;
  rings/elements reverb buffers, plaits workspace all fit) — placement-new +
  `Init()` per switch. Persistent side: platform+USB+I2S ≈ 60-90 KB, mod
  engine ≈ 8 KB.
- **SRAM window**: the four modules' `.time_critical.*` sections total
  ≈ 450 KB — cannot all be resident. Mechanism: regenerate the RAM_CODE
  patches with module-prefixed section names (`.tc_plaits.<token>`,
  `.tc_rings.<token>`, …); custom linker fragment places them ALL in a
  flash-resident output section (NOT in crt0's .data copy) and reserves a
  NOLOAD SRAM window; at switch, copy the selected module's symbols
  (flash → SRAM, ~120 KB ≈ 60 ms) via `__start_/__stop_` section symbols.
  Window target **≈ 120-140 KB** — each module's tiered hot set must fit:
  rings 58 ✓, elements ~30 ✓, clouds 68 (spectral's 56 KB CMSIS tables move
  to flash → spectral mode excluded in combined v1, restored if window
  allows), plaits 272 → re-tier to ~120 (voice path + core LUTs + hottest
  engines; the long-tail engines run from flash — the sweep harness decides
  which fit; worst flash-resident engines may exceed budget and are documented
  per-engine in the UI, mirroring the plaits T3 tiering method).
- **Swap semantics**: audio muted (I2S silence) → copy → placement-new →
  Init (fresh module state; factory defaults) → unmute. MIDI/LED/USB state
  untouched. Mod engine keeps running (its destinations re-resolve to the new
  module's map).

## UART protocol (C3 ↔ RP2350, 921600 8N1)

Frame: `[0x7E][len:u8][type:u8][payload…][crc8]`. Types: `MIDI` (payload =
4-byte USB-MIDI event packet), `SWITCH` (module index), `MOD_SET` (engine
settings), `CHORD_ROUTE` (v2), `TELEM` (RP2350→C3: active module, param
echo, meters, mod curves for the screen). Both sides survive link loss; MIDI
never depends on the link (DIN + USB direct).

## Modulation engine (persistent)

4× LFO (wave, rate 0.05-50 Hz, sync/free, phase), 4× Euclidean trigger
(steps/pulses/rotation, MIDI-clock sync), 2× rhythmic gate (pattern/gate
length), 2× ADSR (gate-follow from note stack). Outputs route per module into
the existing shared-float/pending machinery (destinations = the module's CC
map + trigger maps: plaits trigger, rings strum, clouds freeze/trig). Cost
target ≤ 50 µs/block; engine state in permanent .bss (outside arenas);
MIDI-clock listener shared with the MIDI funnel.

## Risks

- **SRAM window fit** is the schedule driver: plaits' re-tiering to ~120 KB
  needs its own sweep pass; if the window must grow, clouds spectral is the
  designated sacrifice (flash CMSIS tables).
- **Plaits long tail in flash**: engines > ~125 µs sustained (SRAM basis)
  will exceed budget from flash; per-engine UI notes + possible re-tiers.
- **Swap clicks**: 60 ms mute must be click-free (I2S silence write + ramp).
- **C3 single core**: NimBLE + screen + mux on one core — line-based flushes,
  no full-framebuffer mode.
- **Live swap while chained (v2)**: swapping either slot re-runs its Init;
  chain re-patches automatically (routing is persistent state, not module
  state).
