# Combined RP2350 ("rack") — all four modules, live switch, C3 UI, mod engine

Goal: ONE firmware running the four accepted ports (Elements, Clouds, Plaits
98-engine, Rings MiniElements) with live module switching, a persistent
modulation engine, and a hardware UI on a separate ESP32-C3. Serial chaining
(A→B) is v2. Plan doc supersedes none of the per-port plans; the four ports
remain the audio truth — this project composes them.

## Executing from a fresh session

Read, in order: **this doc** (all decisions + rationale are final — do not
re-litigate them), **`.superpowers/sdd/progress.md`** sections for the plaits
and rings ports (fork survey facts, RAM/sweep numbers, patch mechanics,
lessons), **`docs/PORTING-HIGHLIGHTS.md`** (the law), and the four reference
projects' patch chains (`tools/patches/<module>/`) — they are the material
T1 regenerates. Never hand-edit `lib/`; never commit without ledger updates;
acceptance builds come from a clean `.pio` of the committed state.

**ORCHESTRATION protocol — the session agent orchestrates; subagents execute**
(the ledger `.superpowers/sdd/progress.md` holds the rack task-status table):

1. The kickoff session's agent = orchestrator. It reads the plan + ledger,
   then executes the task table **sequentially** (T1 → T2 → T3 → T4; T5
   additionally gates on DSP acceptance + the user's hardware being present;
   T6 on T2/T3; T7 last). For EACH task it spawns ONE subagent
   (general-purpose) with a prompt containing: the read order (this doc,
   ledger plaits/rings sections, PORTING-HIGHLIGHTS §2 patch recipe), the
   task scope + acceptance gate verbatim, the constraint set (no commits,
   read-only submodules, never hand-edit `lib/`, patch-diff recipe, no
   scripted file edits), and the report-back format. Hardware operations
   (flashing, bench sweeps, MIDI tests) are NEVER delegated to subagents —
   the orchestrator does them in its own context between subagent tasks.
2. After each subagent lands: the orchestrator verifies the acceptance gate
   itself (build, nm checks, bench test on hardware where the task defines
   one), updates the ledger row (Status / Committed hash / Notes) + appends
   a dated findings section, commits `[Add]/[Fix]/[Update] rack-rp2350: …`,
   pushes, then proceeds to the next task.
3. A task that cannot reach its gate: record `blocked` + findings, report to
   the user, STOP — do not start dependent tasks. Gates that need the user
   (T5 hardware, T7 acceptance) pause the orchestrator the same way.
4. The DSP-acceptance checkpoint (after T4) is a natural stopping point:
   report all bench results to the user before proceeding to T5/T6/T7.

## Hardware topology

```
[16 pots]─HC4067─┐
[encoder+sw]─────┤ ESP32-C3 (UI MCU, NimBLE)          DIN MIDI IN (6N138 opto)
[BLE-MIDI]───────┤  │  settings/switch cmds,           DIN MIDI OUT
[IPS SPI screen]─┘  │  BLE-MIDI as 4-byte pkts             │
                    ▼ UART 921600, framed                  ▼
        RP2350: UART ingest shim ─┐
        UART1 31250 DIN parser ───┤→ midiHandleEventPacket (ONE funnel:
        USB device + PIO-USB host ┘   device/host/DIN/BLE/UI all 4-byte pkts)
        core 1 render: [mod engine (persistent)] → active module(s) → I2S
```

Pin plan (RP2350): UART1 DIN on free GPIOs (final pins at bring-up; no
collisions with I2S 6/7/8, host 14/15, LED 22, native USB). C3↔RP2350 UART on
two more free GPIOs. C3: HC4067 = 1× ADC1 + 4 addr lines, encoder 2+1 GPIO,
screen = hardware SPI (SCK/MOSI/CS/DC/RST/BL). All 3.3 V.

## Decisions

| Decision | Choice | Why |
|---|---|---|
| UI MCU | ESP32-C3 via UART | Only part with a radio (BLE-MIDI must terminate there); isolates screen/mux/BLE from the proven audio cores |
| Switching | **Live swap**, no reboot | memcpy module's hot sections into the SRAM window (~60 ms, muted), placement-new state into the arena, Init, unmute |
| Mod engine | **DSP side**, core 1 loop-top, persistent object outside the arenas | Block-boundary alignment, MIDI-clock sync, survives swaps, future audio-rate path |
| Chaining | v2, after switching ships | Plaits@32k rate patch + routing; pair list below |
| Bench control | **DSP-first**: module switch + mod settings via MIDI CC and a serial console until the C3 hardware exists; UI tasks land last | All four modules are already MIDI/panel-testable — the DSP must reach acceptance without any new hardware |
| Presets | **C3 owns the preset bank** (its own 4 MB flash — writes never touch audio); **RP2350 owns serialization + apply** (it holds the state); bench phase = serial console dump/load; boot restores last state | RP2350 flash erase/program stalls XIP (audio must mute — unacceptable for saves); the C3 is already the system controller; mapping (pot→param) is UI-side state so it belongs in the same bank |
| MIDI funnel | Everything becomes 4-byte USB-MIDI event packets → existing `midiHandleEventPacket` | Zero changes to accepted module code; UI injects the same bytes the panels send |
| Common rate | 32 kHz for chaining (v2); per-module native rates while switched (48k plaits / 32k others) | Ring/Clouds heavy modes exceed budget at 48 kHz; Plaits at 32k = 1.5× cheaper |

## SRAM architecture (the hard part)

- **Arenas (main.cpp-side, no lib patches)**: object arena 128 KB (largest
  state = rings::Part 123.4 KB) + buffer arena 192 KB (clouds large+small;
  rings/elements reverb buffers, plaits workspace all fit) — placement-new +
  `Init()` per switch. Persistent side: platform+USB+I2S ≈ 60-90 KB, mod
  engine ≈ 8 KB.
- **SRAM window**: the four modules' `.time_critical.*` sections total
  ≈ 450 KB — cannot all be resident. Mechanism: regenerate the RAM_CODE
  patches with module-prefixed section names (`.tc_plaits.<token>`,
  `.tc_rings.<token>`, …); custom linker fragment places them ALL in a
  flash-resident output section (NOT in crt0's .data copy) and reserves a
  NOLOAD SRAM window; at switch, copy the selected module's symbols
  (flash → SRAM, ~120 KB ≈ 60 ms) via `__start_/__stop_` section symbols.
  Window target **≈ 120-140 KB** — each module's tiered hot set must fit:
  rings 58 ✓, elements ~30 ✓, clouds 68 (spectral's 56 KB CMSIS tables move
  to flash → spectral mode excluded in combined v1, restored if window
  allows), plaits 272 → re-tier to ~120 (voice path + core LUTs + hottest
  engines; the long-tail engines run from flash — the sweep harness decides
  which fit; worst flash-resident engines may exceed budget and are documented
  per-engine in the UI, mirroring the plaits T3 tiering method).
- **Swap semantics**: audio muted (I2S silence) → copy → placement-new →
  Init (fresh module state; factory defaults) → unmute. MIDI/LED/USB state
  untouched. Mod engine keeps running (its destinations re-resolve to the new
  module's map).

## UART protocol (C3 ↔ RP2350, 921600 8N1)

Frame: `[0x7E][len:u8][type:u8][payload…][crc8]`. Types: `MIDI` (payload =
4-byte USB-MIDI event packet), `SWITCH` (module index), `MOD_SET` (engine
settings), `PRESET_REQ/PRESET_PART/PRESET_APPLY` (preset save/load chunks),
`CHAIN_ROUTE` (v2), `TELEM` (RP2350→C3: active module, param
echo, meters, mod curves for the screen). Both sides survive link loss; MIDI
never depends on the link (DIN + USB direct).

## Presets

One preset = **full rack state**, split by ownership:

- **RP2350 part** (~1-2 KB, versioned magic): active module id; ALL four
  modules' parameter sets (every CC-map value — so a preset also restores
  params after a swap, which currently re-Inits to factory defaults); mod
  engine state (8 sources: wave/rate/depth/dest/amount/clock-source/division,
  euclid + gate uint32 patterns, ADSR values); clock settings (internal BPM,
  source selection). Binary format with a version byte + crc; the serial
  console dump/load form (bench) is the same blob as hex lines.
- **C3 part**: per-module 16-slot pot→CC mapping, encoder behaviors, UI
  prefs. The C3 consumes mappings directly — they never touch the RP2350.
- **Bank**: C3-side, 16 slots + a separate "last state" autosave (written on
  change with debounce; power-cycle restores exactly where you were). Save
  flow: C3 requests the RP2350 part over UART, appends its own, writes its
  flash — audio untouched. Load: C3 applies its mappings locally, sends the
  RP2350 part; the RP2350 applies via the normal pending machinery (swaps
  module first if the preset says so).
- Bench phase (no C3 yet): console commands dump/load the RP2350 part only —
  this validates the serialization format; the C3 backend is a thin wrapper
  added in T5.

## Modulation engine (persistent)

**Clock bus first** — every source is clockable from Internal or MIDI:
- Internal clock: BPM 20-300, 24 PPQ, block-rate phase accumulator.
- MIDI clock: external 24 PPQ (USB device/host/DIN) with START/STOP/CONTINUE
  handling; pulses are stamped with the render-loop sample counter on arrival
  (core 0) so the scheduler can place ticks at sub-block sample precision —
  no 750 µs quantization of incoming clock.
- Per-source selector: Internal / MIDI, plus a clock division (1/1 … 1/32,
  triplets) where it applies.

Sources (8), all persistent across module swaps:
- 4× LFO: free-running Hz mode OR clocked-division mode; wave (sine/tri/saw/
  square/S&H), phase offset, level. Clocked mode re-phases on external START.
- 4× Euclidean trigger: steps **1-32**, pulses, rotation (uint32 mask);
  tick = selected clock division.
- 2× rhythmic gate: on/off pattern **length 1-32** (uint32 mask), gate
  length per step, same clocking.
- 2× ADSR: gate-follow from the note stack OR clock-retrigger mode
  (division-selected); full A/D/S/R ranges.

Outputs route per module into the existing shared-float/pending machinery
(destinations = the module's CC map + trigger maps: plaits trigger, rings
strum, clouds freeze/trig). Cost target ≤ 50 µs/block; engine state in
permanent .bss (outside arenas). Bench settings via MIDI CC + serial console
until the C3 lands; C3 MOD page writes the same settings later.

## T5 UI/UX design (2026-11-08 — user hardware spec; replaces the T5 row's "menu navigation" idea: NO scrolling menus, fixed pages only)

### Hardware (user-specified)

- Screen: **ST7789P3 IPS, 284×76 wide bar** (landscape). ST7789 native panels
  are 240×320 — bring-up step 1 is discovering the real window/offsets of
  this bar (likely a masked/cropped wide panel) and locking them in the
  driver. Hardware SPI, dirty-row flushes.
- Pots: 16 analog via HC4067 (1× ADC1 + 4 addr lines), physically arranged
  **3 rows: 6 top / 4 middle / 6 bottom** — the screen mirrors this exactly.
- Encoder: rotary + push (3 GPIOs, quadrature interrupts).
- BLE-MIDI: NimBLE → 4-byte MIDI packets inside `MIDI` frames.
- Fonts: **digi-slim @ 6 px height = labels; digi-one @ 5 px height =
  values**, converted to C arrays with `ttf2c.py` from
  `/home/schrab/Projects/ctag-tbd/UI/fonts/` (worked example:
  `norns_ext_gen.py` → `Norns_ext.c`).

### Screen layout (284×76)

```
┌────────────────────────────────────────────────────────────┐
│ ELEM·P1   INT 120.0   chain:off   ▸MOD:0        MIDI ●     │ ← status strip
│ BOW    BLOW   STRKE  CONTOUR  PITCH  MODE                  │ ← row 1 labels (6 cells)
│  162    47     51     50      0     MOD                    │ ← row 1 values
│                                                            │
│ FLW 11    TALLE 17      GEOM 25      BRIGHT 40             │ ← row 2 (4 cells, wider)
│                                                            │
│ TIME   TIMRE  TIMRE  DAMP    POS     SPACE                 │ ← row 3 labels (6 cells)
│  162    47     51     50      0      MOD                    │ ← row 3 values
└────────────────────────────────────────────────────────────┘
```

- The 3 cell rows **mirror the 3 physical pot rows** (top 6 / middle 4 /
  bottom 6); each cell = label (digi-slim 6 px) over value (digi-one 5 px).
  Middle-row cells are wider (~70 px vs ~46 px) — longer names live there.
- Status strip (~10-12 px): module name + page, clock source/BPM (or MIDI
  tick rate), chain state (`off` / `A→clouds`), mod-assign mode indicator,
  MIDI activity dot. The strip is the page indicator — no menu chrome.
- Value = the param's 0-127 CC value; a 2 px underline bar per cell
  (0-127 fill) gives one-glance scanning across 16 pots.
- **Color rules (IPS, ≤3 hues)**: labels gray-white; mod-routed params get a
  cyan label (the routed source's number shows in the value line as
  `MOD:n` suffix or replaces the number while mod-active); chain-B-related
  cells (when the module is B) tinted; clamped/rejected CC flashes red for
  ~300 ms. Everything else monochrome.

### Pages (fixed, encoder-rotated — no menus)

Encoder **rotate = page cycle**; every param is always visible on its page.
Per-module page tables live in the RP2350 registry (single source of truth —
T4a presets reuse them; the C3 is a renderer/collector, the firmware acks
drive the UI — the panels' lesson).

| Page | Contents (pot → param) |
|---|---|
| P1 | the module's primary 16 CC params in row order (top 1-6, middle 7-10, bottom 11-16) |
| P2 | exists only for modules with >16 params (elements: CC 1/11 + overflow); otherwise a duplicate of P1's most-used 16 (user's "alt layout") |
| MOD-A | 4× LFO: rate ×4, level ×4, wave ×4 (as 0-127 enum), phase ×4 |
| MOD-B | 4× EUclid: steps/pulses/rot ×4 (12 pots) + gate1 len (pot 13) + gate1 gate-length (14) + ADSR1 mode (15) + clock div (16) |
| MOD-C | gate2 + ADSR1/ADSR2 (A/D/S/R) + global clock: BPM pot + clock-source (push to toggle internal/midi) |
| SYS | module select (4 cells, push = activate), chain pair select + engage (push = toggle), presets save/load slot (T4a), telemetry on/off, DIN/UART status |

### Gestures (the whole UI is: turn pots, one encoder)

- **Rotate encoder**: switch page (any page; the strip shows where you are).
- **Push-and-hold encoder + turn a POT** = **mod assignment**: cycles that
  pot's parameter through `[off, src0 … src11]` (one gesture assigns /
  changes / unassigns; the strip shows assign-mode while held). Sends
  `MOD_SET`; the RP2350 validates against the active module's destination
  list (invalid = inert + the cell flashes red) and echoes `TELEM`.
- **Push-and-hold encoder + rotate encoder** = module select overlay
  (release confirms; sends `SWITCH`; works from any page).
- **Encoder push (short, on MOD/SYS pages)**: cycles the page's
  selected/alternate value (e.g. clock source, chain pair slot).
- No long-press timers anywhere else; gestures ≤ 3 and always visible in the
  strip.

### UART mapping (existing protocol; one new type)

- Pot move → `MIDI` frame (CC of the pot's mapped param; send-on-move, 7-bit
  after C3-side calibration).
- Encoder page/module/actions → **`UI_CMD` (NEW type)**: page-request
  (RP2350 replies with the page's `TELEM`), sys toggles. `SWITCH` frames stay
  module-switch (the gesture layer sends them).
- Mod assignment → `MOD_SET` (exists). The RP2350 owns validation (registry
  destination lists, chained clamps) — the C3 never enforces.
- RP2350 → C3: **`TELEM`** = full page snapshot `{page id, 16 × (cc, name,
  value, flags: routed/chain-B/inert)}` on page change + throttled deltas
  (≤ ~20 Hz) for moving values; meters later if the strip has room.

### C3 architecture notes

- **Full framebuffer IS affordable at 284×76** (43 KB of C3 RAM) — a change
  from the plan's earlier "no full framebuffer" stance (that assumed a
  bigger panel). Render cells locally, flush dirty rows only; NimBLE
  (~60 KB) coexists with ~43 KB FB + stacks in ~320 KB.
- HC4067 scan: 500 Hz-1 kHz round-robin, per-pot min/max calibration in NVS,
  send-on-move with a 2-3 count deadband; encoder via interrupt + debounce.
- NimBLE stack: BLE-MIDI device (the plan's role); connection interval
  7.5-15 ms; MIDI frames wrap 4-byte packets unchanged.

### T5 bring-up order (each stage independently verifiable)

1. C3↔RP2350 UART framed link (loopback + latency print on both ends).
2. ST7789P3 bring-up: window/offset discovery → line driver → fonts
   (digi-slim 6 px / digi-one 5 px via ttf2c.py) → static page render.
3. HC4067 pots (calibration, send-on-move → CC) + encoder page switching.
4. `TELEM` page rendering + color rules + status strip.
5. Gestures: mod assignment (`MOD_SET` round-trip) + module-select overlay.
6. NimBLE BLE-MIDI → `MIDI` frames.
7. T7 soak + acceptance.

### T5 acceptance

Screen shows live values per page (± 1 count); encoder navigates all pages;
push-hold+pot assignment round-trips (screen shows the routing, the audio
follows, invalid targets flash); push-hold+rotate swaps modules; BLE-MIDI
plays notes; pot-to-CC latency ≤ ~10 ms; **link loss (UART or BLE) never
affects audio or the MIDI funnel** (the RP2350 rule — the C3 is strictly
additive).

## Risks

- **SRAM window fit** is the schedule driver: plaits' re-tiering to ~120 KB
  needs its own sweep pass; if the window must grow, clouds spectral is the
  designated sacrifice (flash CMSIS tables).
- **Plaits long tail in flash**: engines > ~125 µs sustained (SRAM basis)
  will exceed budget from flash; per-engine UI notes + possible re-tiers.
- **Swap clicks**: 60 ms mute must be click-free (I2S silence write + ramp).
- **C3 single core**: NimBLE + screen + mux on one core. At the actual
  284×76 panel a full framebuffer is only 43 KB and is the chosen design
  (dirty-row flushes); the earlier "no full-framebuffer" rule applied to the
  assumed bigger panel.
- **Live swap while chained (v2)**: swapping either slot re-runs its Init;
  chain re-patches automatically (routing is persistent state, not module
  state).
